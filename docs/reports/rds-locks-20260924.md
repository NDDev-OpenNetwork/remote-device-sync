# State lock ownership — 2026-09-24

The publisher workspace run exposed `Busy` immediately after dropping a policy
store in a persistence-failure test, while other tests spawned crash children.
A deterministic reproducer retained a duplicated lock descriptor, dropped its
owner and attempted reopening: it failed with `Busy` before the correction.

On Linux, duplicated or fork-inherited descriptors share a flock; closing only
one descriptor need not release it. CLOEXEC does not close the child's copy
before exec. This explains the observed race, though the exact original
interleaving was not traced. See [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html).

Atomic state, database and sync receive guards now explicitly unlock on owner
drop. A closing old descriptor cannot release a successor's independent lock.
Lock inodes remain persistent; no retry delay, file deletion or weaker ownership
rule was added. The three descriptor-alias regressions passed, as did discovery
unit tests and the sync unit/journal suites. Full workspace validation continues
with the publisher change; no native macOS or network-filesystem qualification
is claimed. This repairs ownership in W1.4/W1.5/W1.10 without closing those waves.
