# RDS implementation and session-history audit — 2026-09-24

Baseline: `87e7aeabaad861b0d3c63f6641c91539be19a3e0` (v0.1.0, protocol 3).
Scope: the public RDS module, its estate integration, and locally available
development-session evidence. This is an audit and planning change, not a
runtime fix or a deployment attestation. The implementation backlog is in
[remediation-plan.md](../remediation-plan.md).

## Assessment

RDS has a useful Rust foundation, but does **not yet satisfy** the intended
product: dependable, low-latency, independently operated SSH, interactive
desktop and device synchronization on Linux x86_64 and macOS arm64.
Passing compilation and existing tests do not establish those capabilities.

The immediate blockers are authorization lifetime/revocation, trusted name
resolution, safe file assembly, and owned-transport connection establishment.
Ten isolated diagnostic tests reproduced defects on this baseline, despite
the existing all-features suite passing. A finished desktop viewer, native
SSH client/server, production macOS/Wayland backends, automatic session
recovery and a complete GDS enrollment/policy flow remain implementation work.

The register contains **49 findings**: 7 P0, 39 P1 and 3 P2. These include
reproduced defects, code-derived risks and missing capabilities; they are not
49 independently reproduced bugs. The plan defines **79 tasks in 11 waves**,
each with acceptance evidence and dependencies.

Keep the working iroh lane as a comparison and migration fallback while
repairing and completing the owned lane. Replacing it immediately would lose
connectivity capabilities that the owned implementation does not yet provide.
Ownership should mean Rust application code and policies, replaceable
libraries, and explicit OS interfaces; it should not mean inventing new
cryptographic primitives or pretending platform drivers are written in Rust.

## Finding register

Priority: **P0** fixes before expanding deployment or relying on security/data
guarantees; **P1** required for the intended reliable product; **P2** subsequent
capability/maintainability work. Evidence: **R** reproduced, **C** code-derived
behavior/risk, **M** missing implementation or acceptance evidence. A code risk
is not presented as a reproduced production incident. IDs map to the plan.
Paths and symbols below refer to the baseline commit.

### Authorization, discovery and identity

**A01 — P0 / R06: device names are not authenticated at the client.**
[`Client::resolve_name`](../../crates/rds-discovery/src/client.rs) accepts a
plain `key` from `/v1/names`; [`resolve_target`](../../crates/rds-net/src/resolve.rs)
then validates the endpoint's self-signed record for that returned key.
The client has no registry trust anchor or signed name-binding proof. QUIC
correctly authenticates the identity the hostile mapping chose. Transport
encryption therefore does not repair name trust. Return a signed binding or
snapshot and verify issuer, requested name, key, validity and revision at the
client. Add Rust TLS with hostname/trust configuration for the directory;
keep end-to-end signature verification even over TLS.

**A02 — P0 / R01 + C: revocation state and freshness are unreliable.**
[`AgentPolicy::ssh_only`, `replace_denylist`, `revoke`, `watch_revocations`,
`watch_grant`](../../crates/rds-agent/src/lib.rs) use a watch sender whose
initial receiver is dropped. `send` fails without receivers and the error is
ignored, so an initial snapshot can be lost while its revision is marked
seen. Subscription happens after the admission check, and the watchdog waits
for a change without first checking the current snapshot. The polling loop
verifies signatures but not snapshot expiry, has no durable rollback cursor,
and cannot bound staleness during outages. Store independently of observers,
make admission/watch registration atomic, enforce freshness and define
explicit offline admission/active-session policy. Persist revocation state.

**A03 — P0 / R10 + C: failed Authz ACK can disable expiry/revocation.**
[`authorize`](../../crates/rds-agent/src/lib.rs) sets `Granted` and reserves the
grant ID before fallible reply writes. The watcher is only installed after
those writes succeed. Stopping the reply stream leaves an authorized
connection without its watchdog; later scope checks do not recheck validity.
Separate check/set locks also permit concurrent admission races. Use one
authorization state machine with an admission guard, watcher installation,
rollback and connection cancellation. Enforce current validity at service
admission as defense in depth. Test failed ACK, concurrent Authz and teardown.

### Transport and session lifecycle

**T01 — P0 / R09 + C: owned dial does not race viable paths.**
[`noq::Endpoint::connect`](../../crates/rds-net/src/backends/noq/mod.rs) awaits
the first sorted direct address before opening other paths or adding the
relay. A bad/loopback/NAT-unreachable first candidate prevents use of good
candidates or the relay during initial establishment. Default advertising
adds loopback alongside an egress hint; public `addr()` also traverses locals
without the synthetic-address filtering used by `advertised_socket_addrs`.
Implement a deadline-bound candidate race and an independently usable relay
bootstrap, then upgrade to direct. Test multiple hosts, not just loopback.

### File transfer and synchronization

**S01 — P0 / R03: partial destination deduplication cannot assemble.**
[`Journal::seed_from_destination`](../../crates/rds-sync/src/journal.rs) marks
matching destination chunks as present, but does not materialize them in the
parts store or record an immutable source/offset. `assemble` reads parts
unless the entire destination already matches. Thus the identical-file test
passes while the useful partial-delta case fails. Record verified sources or
copy/reflink chunks safely before reporting them present; handle changed-size
files and destination mutations as well.

**S02 — P0 / R04: assembly deletes a legitimate neighboring file.**
`Journal::assemble` appends `.rds-part` to the destination and unconditionally
unlinks that path before exclusive creation. Exclusive creation prevents
following a pre-existing symlink but does not justify deleting someone else's
file. Use an unpredictable, exclusively created, directory-relative temp
owned by this transfer; only remove temp files proven to belong to it.

**S03 — P0 / R05 + C: journal confinement is incomplete.**
`resolve_under` checks the journal directory, but subsequent `parts` and
metadata/temp paths can follow pre-existing symlinks. Canonicalize-then-open
also leaves a race against local path replacement. Use directory-handle
relative operations with no-follow semantics and validated ancestry on both
platforms. Document the local attacker model, including pre-existing state
and concurrent writers. Merely adding another string/canonicalization check
does not establish race-free confinement.

## Rust ownership and Cloudflare decision

Use embedded Rust libraries for transport, TLS, SSH, HTTP, synchronization,
application policy and UI. Own the protocol state machines, session lifecycle,
scheduling and permission model. Isolate OS/driver calls in narrow adapters.
List bundled native code explicitly: OpenH264 and ring are not literally
Rust-only dependencies. Replacing vetted crypto or a working codec without
parity evidence would increase risk. A strict no-native-code build is a
separate compatibility/performance target, not something this baseline meets.
The ring upstream explicitly documents its C/assembly provenance.
([ring upstream](https://github.com/briansmith/ring))

For built-in SSH, evaluate `russh` behind an RDS-owned session interface;
its client accepts an async stream, fitting a QUIC service stream without a
required `ssh` subprocess. This is a candidate integration, not a completed
dependency/security decision.
([russh stream API](https://docs.rs/russh/latest/russh/client/fn.connect_stream.html))

Recommended default connectivity policy: race suitable direct candidates and
an authenticated owned relay; keep a usable relay path while upgrading to
validated direct; add a Rust HTTPS/TCP fallback for networks blocking UDP.
Measure the head-of-line and congestion cost of that fallback rather than
promising equal latency to direct UDP. Prewarming may reduce setup time but
must have explicit battery, socket, privacy and lease budgets.

Cloudflare is optional infrastructure, not the mandatory RDS dataplane.
Public-hostname Tunnel routing and private-network access are different
products/paths: the former's TCP/SSH routing uses client-side helpers and is
not a generic public UDP mapping. Private-network paths with the Cloudflare
One Client can carry network traffic through a managed tunnel, but add
enrollment and routing dependencies. Therefore the earlier blanket claim
that Cloudflare cannot carry UDP in any mode is too broad. Whether a
Cloudflare path improves availability or latency is an empirical question
for the actual devices; this audit measured no such improvement.
([Tunnel routing](https://developers.cloudflare.com/tunnel/concepts/routing/),
[connectivity options](https://developers.cloudflare.com/cloudflare-one/networks/connectivity-options/),
[client architecture](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/configure/route-traffic/client-architecture/))

No additional hosts, paid services or mandatory external runtime daemons are
needed merely to execute this plan. A Cloudflare deployment adapter may be
tested later if the existing network topology justifies it. It must remain
removable without changing RDS identity, grants, SSH or media protocols.

## Closure rule

No finding in this report is closed by this documentation change. A closure
requires the linked plan task, a reproducer/regression test where applicable,
appropriate platform checks, an exact-revision receipt and updated capability
documentation. The ten diagnostic assertions must be inverted into desired
behavior tests when fixes are implemented; a diagnostic test passing here
means the defect exists, not that the product is safe.
